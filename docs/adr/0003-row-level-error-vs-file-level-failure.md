# A broker file fails as a whole; a bad row is flagged and survives

An uploaded file is handled at two levels with deliberately different failure semantics. When no parser recognises the file's layout — an unrecognised or corrupt workbook — that is a **file-level failure**: `ImportParserResolver.resolve` raises `UnsupportedImportFileException` (a `DomainException`), which the edge maps to a 4xx carrying the canonical error body, and nothing is staged. When a *recognised* file contains a bad row — a missing or unparseable date, a `Valor Bruto` that does not equal quantity × price, an unknown side, a blank ticker — that is a **row-level error**: the row still stages with `error` set and `date` possibly null, and `apply` skips it, so one bad row never discards a good file.

The two kinds differ because they are different mistakes. A file the pipeline cannot read has no usable rows at all and is the caller's error to fix and re-upload; recording it as an empty import hides the mistake. A bad row inside a readable file is data to inspect in review, not a reason to reject the rest.

Considered options: **stage every unclaimed file with zero rows** (the previous behaviour — records the raw upload, but leaves a silently empty import that looks successful); **abort the whole file on the first bad row** (one malformed line throws away an otherwise good statement). A missing date is a row-level error, never a fabricated sentinel date, so `import_row.date` is nullable and a trade — which requires a date — is created only from an error-free row.
